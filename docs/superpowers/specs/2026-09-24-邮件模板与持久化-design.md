# 邮件模板重设计、高优先级转发与消息持久化

日期：2026-09-24
状态：已确认，待实现

## 背景与目标

当前项目已能连接 Gotify 的 `/stream` 推送流（`GotifyConnection` + `ListenGotify`），
但 `ListenGotify.onMessage` 只打了一行日志，`templates/message.html` 是个没人引用的孤儿模板，
`GotifyConfig.Mail` 里只有一个 `to()` 且没有任何发信代码。也就是说「邮件通知」这条链路
（提交 `d75e74f`）只搭了架子，没有通电。

本设计要接通三件事：

1. **重新设计邮件模板** —— 重写 `message.html` 的视觉与信息层级
2. **高优先级转发** —— 优先级严格大于 6 的消息转发到邮箱
3. **全量持久化** —— 收到的**所有**消息都落库（H2 验证，不只高优先级）

### 明确不在范围内（YAGNI）

- 不做失败重发队列、不做邮件重试调度
- 不做历史消息的查询 API / UI
- 不对 SMTP 配置做启动期校验（用户明确要求邮箱配置暂时留空）
- 不做 extras 的关联表建模

## 架构

采用**单个编排服务**方案：WebSocket 端点只做转发，业务逻辑集中在 `MessageService`。

```
ListenGotify.onMessage(GotifyMessage)
        │  仅转发，不含业务逻辑
        ▼
MessageService.handle(GotifyMessage)
        │
        ├─ 1. 幂等入库（事务 1，提交）
        ├─ 2. priority > 6 ? ──否──▶ mail_status = NOT_APPLICABLE，结束
        │         │是
        ├─ 3. 渲染 Qute 模板（HTML + 纯文本）
        ├─ 4. 发送邮件（事务外，异常全部捕获）
        └─ 5. 回写状态（事务 2，短事务）
```

选择理由：与现有代码风格一致（`GotifyConnection` 也是普通 `@ApplicationScoped` bean 注入端点），
传输层保持轻薄，且「先入库后发信」的顺序不会渗漏到端点层。
未选 CDI 事件驱动（对单生产者双消费者属过度设计，且状态回写别扭）、
未选端点直接编排两个服务（编排逻辑污染传输层）。

## 数据模型

Panache 实体 `GotifyMessageEntity`，表名 `gotify_message`：

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | **主键** | **直接使用 Gotify 的消息 id，非自增** |
| `app_id` | BIGINT | | 应用 id |
| `title` | TEXT | 可空 | 标题 |
| `message` | TEXT | 可空 | 正文 |
| `priority` | INT | | 优先级 |
| `pushed_at` | TIMESTAMP | 可空 | Gotify 的 `date`，存 UTC 瞬时点 |
| `extras_json` | TEXT | 可空 | `extras` 序列化为 JSON 字符串 |
| `mail_status` | VARCHAR | 非空 | 见下方枚举 |
| `mail_error` | TEXT | 可空 | 发信失败原因，成功时为 null |
| `received_at` | TIMESTAMP | 非空 | 本地入库时间 |

### 为什么 `id` 直接作主键

去重语义就是「Gotify 消息 id 唯一」。用 `id` 作主键让**数据库在结构层面**保证幂等，
而不是依靠应用层「先查后插」——后者存在竞态窗口。

插入前用 `findByIdOptional(id)` 判断。**若已存在，`handle()` 立即 return，
既不更新已有行、也不发信**（保留首次的 `mail_status`，重复投递不产生第二封邮件），
仅打一条 DEBUG 日志。这是去重的完整语义，不留歧义。

### 为什么 `extras` 存 JSON 字符串

`extras` 是任意键值对，Gotify 自身 schema 并不固定。为它建关联表属于过度设计。

### `mail_status` 取值

| 值 | 含义 |
| --- | --- |
| `NOT_APPLICABLE` | 优先级未达阈值，或收件人未配置，本就不该发信 |
| `PENDING` | 达到阈值，待发（入库时的初始态，也是发信中途崩溃后的可识别残留） |
| `SENT` | 发送成功 |
| `FAILED` | 发送失败，原因记于 `mail_error` |

## 事务边界

**这是本设计最容易做错的地方，需严格遵循：**

- **事务 1（入库）**：仅写入实体并提交。保证「消息一定会落库」。
- **事务外（发信）**：SMTP 可能耗时数秒。若与入库同事务，会长期占用数据库连接，
  且发信失败会连累已入库的数据回滚——这与「先持久化」的要求直接矛盾。
- **事务 2（回写）**：发信结束后开一个短事务，仅更新 `mail_status` 与 `mail_error`。

因此 `handle()` 方法**本身不能标 `@Transactional`**（否则整个方法被包进一个事务，
发信就被裹进去了）。入库与回写各自通过独立的 `@Transactional` 方法完成，
注意 Panache 的 `@Transactional` 走 CDI 代理，**同类内部自调用不会生效**，
需拆到不同 bean 或使用 `@Inject` 自引用 / `Transactional.TxType` 显式处理。

**失败处理原则：任何邮件相关异常都不得中断 WebSocket 监听循环。**
`handle()` 用一个覆盖步骤 2–5 的 try/catch，把异常落到 `mail_status=FAILED` + `mail_error`，
并打 ERROR 日志。

## 邮件模板重设计

现有 `message.html` 的问题：优先级只是一个藏在 footer 的裸数字，高优先级邮件毫无视觉区分度；
正文不折行，长串会撑破布局；没有纯文本副本；标题/正文为 null 时无兜底。

### 优先级配色（按 Gotify 惯例）

| 优先级 | 语义 | 配色 |
| --- | --- | --- |
| ≤ 3 | 低 | 灰蓝 `#57606a` |
| 4–6 | 中 | 琥珀 `#bf8700` |
| 7 | 高 | 橙红 `#d1550d` |
| ≥ 8 | 紧急 | 正红 `#cf222e` |

配色由 `MessageService` 在渲染前算好并作为模板参数传入，
**模板中不写分支判断逻辑**（Qute 模板保持只负责展示）。

### 具体改进点

1. **顶部色条 + 优先级徽章**，取代原本藏在 footer 的裸数字
2. **时间显式转 `Asia/Shanghai` 格式化**。必须如此：`GotifyMessage` 的类注释已指出
   Jackson 默认 `ADJUST_DATES_TO_CONTEXT_TIME_ZONE` 会把 `date` 归一化到 UTC，
   直接用会显示错时区。
3. **正文 `white-space: pre-wrap` + `word-break: break-word`**，长 URL 不再撑破布局
4. **`extras` 非空时渲染键值区块**，为空则整个区块不输出（Qute `{#if}`）
5. **纯文本副本 `message.txt`**，与 HTML 组成 multipart/alternative
6. **null 兜底**：`title` 为 null 时显示「(无标题)」，
   `message` 为 null 时显示「(无正文)」，`pushed_at` 为 null 时显示「(未知时间)」

### 转义（安全要求）

**正文与标题一律严格 HTML 转义，按纯文本处理。**
采用 Qute 的 HTML 输出模式（默认模板后缀 `.html` 即按 HTML 转义），
对变量使用 `{title}` 而非 `{title.raw}`。

理由：任何能向 Gotify 投递消息的人（或任何能调用 Gotify API 的上游）都能借此
向收件邮箱注入任意 HTML —— 钓鱼链接、追踪像素等。转义是安全底线。

代价：Gotify 消息里原本的 HTML 标签会显示为可见的尖括号。这是有意接受的取舍。

## 配置

`application.yaml` 新增：

```yaml
gotify:
  mail:
    to: ${GOTIFY_MAIL_TO:}
    # 严格大于该值才转发（即 7 及以上）
    priority-threshold: 6

quarkus:
  datasource:
    db-kind: h2
    jdbc-url: jdbc:h2:file:./data/gotify;AUTO_SERVER=TRUE
  hibernate-orm:
    database:
      generation: update
```

`GotifyConfig.Mail` 增加 `priorityThreshold()`（`@WithDefault("6")`），保留 `to()`。

### 「邮箱配置留空、不验证可用性」的落地方式

这里有个反直觉的陷阱：**Quarkus Mailer 是构建期扩展，SMTP 配置缺失时启动不会报错**，
而是在真正发信那一刻才抛异常。所以「不校验」不等于「什么都不做」，需要：

1. `to()` 为空时在 `MessageService` 中**提前短路**，直接把 `mail_status` 记为
   `NOT_APPLICABLE` 并打 WARN，**不让 Mailer 抛异常污染日志**
2. **不对 SMTP 配置做任何启动期校验**（满足「暂时留空」的要求）
3. 所有发信异常统一捕获（见「事务边界」）

### 数据库文件位置

`./data/gotify.mv.db`（相对工作目录，H2 会自动补 `.mv.db` 后缀）。
需在 `.gitignore` 加入 `data/`。

`AUTO_SERVER=TRUE` 允许外部工具同时连库查看数据，便于验证期排查。

`quarkus.hibernate-orm.database.generation=update` 让 Hibernate 自动建表，
满足「暂时只做验证」的诉求，不引入 Flyway。

这是冒烟测试要覆盖的第一项。

## 邮件内容

- **收件人**：`gotify.mail.to` 逗号分隔列表
- **主题**：`[Gotify][优先级 N] 标题`，让高优先级在收件箱列表里即可辨认
- **正文**：HTML + 纯文本双部分

## 测试策略

用 `@QuarkusTest`，H2 用独立的测试库文件（不用内存库，以便验证真实的建表与文件行为）。

| 测试 | 断言 |
| --- | --- |
| 全量持久化 | 优先级 1 的消息也入库 |
| 去重 | 同一 id 投递两次，库中仅一行，且只发一次信 |
| 阈值边界 | 优先级 7 触发发信；优先级 6 **不**触发（严格大于） |
| 发信失败不回滚 | 发信抛异常时消息仍在库中，且 `mail_status=FAILED` |
| 收件人为空 | 高优先级消息入库且 `mail_status=NOT_APPLICABLE`，不抛异常 |

**邮件不发真实 SMTP**：用假发信出口（`@Alternative` 实现或 mock Mailer）替换，
断言「是否触发发送」而非真的投递。这满足「暂时只用本地数据库做验证」。
